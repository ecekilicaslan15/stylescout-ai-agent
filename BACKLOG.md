SCOUT-001 — Verify mode + provenance against real behavior
Title: Reality-check the completed mode/provenance work end-to-end Goal: Confirm the three modes and source/owned metadata behave as the summary claims, on the live deployment, not just in tests. Why this task exists: Tests passing ≠ product working. Prior summaries have overstated completeness. Before building on modes, prove they hold under manual use. Scope:
Run the same outfit request in all three modes; confirm outputs differ.
Confirm Mode 1 returns only owned items, every one badged Owned.
Confirm Mode 2 caps suggested items at 2.
Confirm Mode 3 annotates ownership after generation.
Confirm the change is actually live on Render, not only local. Out of scope: Any new feature. This is verification only. Technical approach: Manual test matrix (3 modes × empty/partial/full wardrobe). Record actual vs expected in docs/AUDIT.md. Compare local container behavior to the deployed URL. Acceptance criteria:
A filled test matrix in docs/AUDIT.md with pass/fail per cell.
Any divergence from the summary is logged as a follow-up task, not silently fixed.
The deployed URL reflects the mode work (or a deploy is triggered). Files that will probably change: docs/AUDIT.md only. Risks: Discovering a mode doesn't actually differ → becomes a bugfix task. That's the point. Dependencies: none. Difficulty: S · Time: 1–2h Required tests: none new; this consumes existing tests as evidence. Commit: docs: record verified mode/provenance behavior matrix PR title: Verify mode and provenance behavior end-to-end Docs: docs/AUDIT.md matrix section.

SCOUT-002 — Consolidate the validation gate
Title: Unify output validation into a single explicit gate Goal: One clear validation pipeline every outfit passes through: schema → referential → constraint → coherence, with exactly one repair attempt, then deterministic fallback. Why this task exists: The mode work already added "referential integrity checks." Scattered checks are hard to reason about and hard to demo. Centralizing them is the portfolio-legible win, and it's the seam the LLM will later plug into. Scope:
Locate every existing validation check (referential, provenance, caps).
Route them through one named component/function invoked once per outfit.
Add missing layers: schema shape, coherence (no duplicate slots, required slots present).
On failure: one repair attempt (deterministic reorder/refill), then rule-based fallback with a user-visible reason. Out of scope: LLM repair (no LLM yet). Fuzzy matching. Technical approach: Prefer a pure function validate_outfit(outfit, context) -> ValidationResult over a new agent. Pydantic for schema. Reuse existing referential checks; do not rewrite them. Acceptance criteria:
All outfit responses pass through the single gate.
Constraint violations (Mode 1 non-owned item, >2 suggested in Mode 2) are impossible to return — enforced here, not upstream only.
A deliberately corrupted outfit fixture is caught and repaired or falls back. Files that will probably change: orchestrator/fashion_orchestrator.py, a new services/outfit_validation.py, models/. Risks: Duplicating checks already inline → net negative. Mitigate by grepping first (see reality check). Dependencies: SCOUT-001. Difficulty: M · Time: half day Required tests: corrupted-fixture repair test; Mode 1 non-owned rejection test; Mode 2 cap test routed through the gate. Commit: feat: consolidate outfit validation into a single gate PR title: Single validation gate with repair + deterministic fallback Docs: docs/ARCHITECTURE.md validation section; docs/DECISIONS.md record.

Diagnose the taxonomy mismatch (singular/plural, case, frontend vs DB values).
Normalize category values at one boundary. Out of scope: New categories, tagging UI. Technical approach: Establish one canonical category vocabulary. Normalize on write and on query. Do not scatter .lower() calls across the frontend. Acceptance criteria:
Every category tab shows its items; "All" shows the full 28.
A test asserts filtering returns non-empty for a seeded category. Files that will probably change: wardrobe/normalization.py, frontend/index.html, wardrobe repository. Risks: Fixing display but leaving seed data inconsistent. Normalize the data too. Dependencies: SCOUT-001. Difficulty: S · Time: 1–2h Required tests: category-filter returns expected count. Commit: fix: normalize wardrobe categories so filters return items PR title: Fix category filtering taxonomy mismatch Docs: docs/DECISIONS.md: canonical category vocabulary.
SCOUT-004 — Fix image/label integrity and UI honesty
Title: Never show an image or trace label that contradicts reality Goal: Item cards show a correct image (or a neutral placeholder), and pipeline trace labels reflect the real execution path. Why this task exists: Observed live: a "BEIGE BLAZER" card showed a blue suit, and the UI credited "STYLIST AGENT / MEMORY AGENT" while USE_LLM=False. Both are portfolio-damaging false claims. Scope:
Root-cause the image mismatch (random placeholder, index offset, missing url).
Wrong image → correct image or category silhouette placeholder. Never a contradicting photo.
Rename trace labels to the real path (WARDROBE SERVICE, MEMORY SERVICE, RULE-BASED COMPOSER), driven from one place so it flips to "STYLIST AGENT (LLM)" automatically later. Out of scope: Image upload (SCOUT-006). Technical approach: Single source for trace labels tied to whether an LLM actually ran. Deterministic placeholder per category. Acceptance criteria:
No card shows an image contradicting its label.
Trace labels match execution path and come from one code location. Files that will probably change: frontend/, seed/wardrobe data source, services/stylist_notes_builder.py. Risks: none significant. Dependencies: SCOUT-001. Difficulty: S · Time: 1–2h Required tests: none (UI); optional snapshot of label source. Commit: fix: image/label integrity and honest pipeline trace labels PR title: UI honesty — correct images and real trace labels Docs: docs/DECISIONS.md: UI reflects real execution path.
SCOUT-005 — Add-item form (create wardrobe items)
Title: Let users add their own wardrobe items Goal: A 6-field form (name, category, color, formality, season, optional image url) creates a persisted wardrobe item with user_id. Why this task exists: Without user-owned data the product is a fixed demo. This is the smallest step to "real product." 
Scope: Create + validate + persist + render new item. user_id on every record (no auth; single tenant id for now). Out of scope: Image upload, auto-tagging, background removal, edit/delete (next task). Technical approach: New POST endpoint reusing the wardrobe repository. Server-side validation via Pydantic. Frontend form posts and re-renders the grid. Acceptance criteria:
Adding an item persists it and it survives container restart (given persistent DB path).
Invalid input returns a clear 4xx, not a 500.
New item carries user_id, source="wardrobe", owned=true. Files that will probably change: api/main.py, wardrobe repository, frontend/, models. Risks: Form scope creep. Hold to 6 fields. Dependencies: SCOUT-003. Difficulty: M · Time: half day Required tests: create success; create validation failure; persistence read-back. SCOUT-010 — Deep-link shopping provider
Title: Turn search_spec into real, pre-filtered marketplace search links Goal: A provider that generates correct search URLs (query + size + price ceiling + condition) into ≥2 real platforms. Why this task exists: Legal, free, honest, and genuinely useful. No API, no scraping, no fake data. This is the "intent generator upstream of marketplaces" thesis made concrete. Scope: Provider interface + DeepLinkProvider. Result kind search_entry_point — no prices, no fake listings. Out of scope: Live inventory, affiliate networks, curated demo catalogue. Technical approach: Map SearchSpec fields to each platform's public search-URL params. Provider registry so more can be added. Graceful degradation to a bare search page if params change. Acceptance criteria: Two clicks from a gap to a correctly pre-filtered real search with size + price applied. No price is ever displayed on a deep link. UI clearly labels these as searches, not listings. Files that will probably change: new services/shopping/, frontend/. Risks: Platform URL schemes change → tests + fallback. Dependencies: SCOUT-009. Difficulty: M · Time: half day Required tests: URL construction per platform; fallback on missing params. Definition of Done (whole project)
The MVP is portfolio-complete when all of the following hold:
Product honesty
Three modes produce genuinely different, correct outputs; Mode 1 never returns a non-owned item.
Every item is labeled owned or suggested; no image contradicts its label; no trace label claims work that didn't happen.
No fake product or price data appears anywhere; shopping is deep links only.
Real usage
A user can add, edit, and delete their own wardrobe items and save outfits.
State persists across a session and a container restart (or the ephemeral limit is clearly documented).
Intent & shopping
Every suggested item yields a valid search_spec honoring declared size/budget/exclusions.
Each gap reaches a correctly pre-filtered real marketplace search in two clicks.
Architecture
Exactly two agents; everything non-reasoning is a service; the rule-based composer remains as fallback.
One validation gate enforces schema, referential, constraint, and coherence rules with a repair-then-fallback path.
No dead surfaces; dependency list matches actual imports; image size is reasonable.
Quality
Eval harness reports real metrics (including unfavorable ones); Mode 1 compliance is 100%.
CI runs the suite on every push and is green.
Deployment & docs
Live URL loads and works (within one cold-start retry); limits documented.
README explains the project in five minutes, includes the deterministic-vs-LLM boundary, a "What this does not do" section, metrics, and the live link.
A tagged v1.0-portfolio release with screenshots and a 90-second demo video.
Explicitly NOT required for done: authentication, payments, live inventory, auto-tagging, background removal, virtual try-on, learned personalization, LLM integration. These are post-MVP; the architecture leaves room for them (provider interface, user_id, search_spec) without requiring them.
